## 1. Veredicto en tres frases

1. **La comparación de tokens es degenerada y no debe reportarse como ahorro:** los tres

### P1 — Crítica · El fallback `||` re-ejecuta la compuerta que falló

**Qué.** El bucle de §8.2 usaba `(command -v timeout && timeout 180 node "$f" || node "$f")`.
`||` no distingue *"`timeout` no está instalado"* de *"la compuerta falló"*.

**Consecuencias.** (a) Cada compuerta roja se ejecutaba **dos veces**; el exit code reportado
era el de la segunda corrida. (b) Si `timeout` existe y la compuerta se **cuelga**, el fallback
la relanza **sin timeout**: la auditoría cuelga. Un protocolo que persigue falsos verdes tenía
un falso rojo que se re-ejecuta solo.

**Proof.**
```bash
printf 'console.log("EJECUTADA")\nprocess.exit(1)\n' > /tmp/demo.mjs
out=$( (command -v timeout >/dev/null 2>&1 && timeout 180 node /tmp/demo.mjs || node /tmp/demo.mjs) 2>&1 )
echo "$(echo "$out" | grep -c EJECUTADA) veces ejecutada"   # -> 2
```
Medido en este entorno: `timeout presente? SI` · `veces ejecutada: 2`.

**Arreglo.** `if command -v timeout …; then …; else …; fi`. Verificado en §8.2 y documentado
como trampa en **A.11**.

### A.1 S2 resuelto: el runner de sondas, y el defecto que apareció al construirlo

El gap era: **25 sondas conductuales se generaban y nadie las ejecutaba.** El propio archivo lo
admitía a medias —"responderlas cuesta inferencia"— y ahí quedaba.

**La pieza que faltaba era chica y no obvia:** cada sonda ya trae su criterio (`expected` y
`forbidden`, regex), así que **el juez es determinista**. Lo único que necesita un modelo es
*producir* la respuesta. Eso parte el costo en dos y sólo uno cuesta inferencia:

| Paso | Comando | Costo |
| :--- | :--- | :--- |
| Emitir | `pnpm aoi:probes` | 0 tokens |
| Responder | el harness, con un modelo | inferencia |
| **Juzgar** | `pnpm aoi:probes:judge <answers.json>` | **0 tokens** |

#### El defecto que el control negativo destapó

Al probar el juez con una batería de **no-respuestas**, dos sondas **aprobaron "No se."**:

```
LAXO: zero-task-footprint aprueba "No se."
LAXO: service-discovery-mandatory aprueba "No se."
```

Causa raíz, y es de diseño: **`expected` está sobrecargado a propósito.** Tiene que aparecer
en el contexto de la fase (test de evidencia) *y* describir una respuesta. Las dos tiran en
direcciones opuestas: para pasar el test de evidencia el patrón tiene que estar en la prosa, y
la prosa usa "no"; así que `\bno\b` terminó midiendo **la palabra** y no la decisión.

Y es peor que "No se.": `service-discovery-mandatory` aprobaba también una respuesta
**invertida** —*"No hay problema, podés saltearla sin drama"*— porque `no` niega otra cosa y
`salt` está a 20 caracteres. Regex no parsea intención; el criterio tiene que exigir la
negación **del permiso**, pegada a la negación.

**Sin el control negativo, el runner habría reportado *"25/25 conductas correctas"* sobre
respuestas que no decidían nada.** El falso verde, fabricado por el instrumento que existe para
cazarlo.

**Arreglado en tres capas:**

1. **Guardia de evasión** en el juez: una respuesta que declara no poder decidir (incluida la
   salida que el propio prompt ofrece: `NO PUEDO DETERMINARLO CON ESTE CONTEXTO`) **falla**.
   Rendirse es fallar la decisión, no acertarla.
2. **Piso de longitud**: cada escenario pide la decisión *y su porqué*, así que una respuesta de
   una palabra no puede contener el porqué.
3. **Los dos criterios, reescritos** para exigir la negación del acto.

Y **dos compuertas permanentes** en `behavioral-runner.test.mjs`, que son lo que impide que
vuelva:

| Compuerta | Qué hace |
| :--- | :--- |
| `ninguna sonda aprueba una evasión` | batería de 10 no-respuestas contra las 25 sondas |
| `ninguna sonda aprueba una respuesta sustantiva pero INCORRECTA` | el caso difícil: larga, con porqué, y que decide al revés |

**Proof.**
```bash
node scripts/sdd-lifecycle/behavioral-runner.mjs --judge /tmp/aoi-answers-malas.json
# -> 0/25 correctas  (antes del arreglo: 2/25 — las dos laxas)
```

#### El techo, escrito en la salida

El reporte del runner declara por escrito qué prueba y qué no, **porque `expected` es una
condición necesaria y no suficiente**:

> · SÍ: cada respuesta no es una evasión, lleva el porqué, y contiene el patrón que la fase
> también contiene.
> · NO: que el modelo haya **usado** la evidencia del contexto.
> · Un `pass` acota el espacio de respuestas incorrectas. No lo cierra.

### A.3 Hallazgo nuevo: una entidad inexistente pasaba como "sin contrato"

Apareció al completar la Fase 12, probando los tres caminos de exit del Invariant Gate en vez
de sólo el verde.

```
$ node scripts/sdd-lifecycle/invariant-gate.mjs --entity "ENTIDAD-QUE-NO-EXISTE" --exit-code
   EXIT=0        # ← reportaba SKIPPED
```

**Causa raíz.** `icm` no usa códigos de salida: para una entidad desconocida contesta
`no facts for <entity>` **con exit 0**. La única señal es ese texto, y `readFactsFromIcm`
devolvía `ok: true` con texto vacío. El CLI veía cero reglas, reportaba `SKIPPED`, y salía 0.

**Por qué importa.** `SKIPPED` significa "el workspace no pasó por `/sdd-frame`" y es legítimo.
Pero un **typo** en el nombre —`--entity "AOI TEST"` en vez de `"AOI TESTS"`— producía el mismo
resultado: **pasaba como "no hay contrato que incumplir"**. Un falso verde en el gate que existe
para cazar falsos verdes, y encontrado en el mismo camino que la §11.9 arregló para la entidad
**inferida**.

**El comentario del test ya describía el defecto.** `invariant-gate.test.mjs` decía:

> *"A failed read MUST explain itself; the CLI turns this into a blocking exit 2 rather than an
> empty fact list that would look like a clean SKIPPED pass."*

El intento estaba escrito y el código no lo hacía: la aserción sólo verificaba **la forma**
(`typeof ok === 'boolean'`), así que el gap sobrevivió a un test cuyo propio texto lo nombraba.

**Arreglado** distinguiendo las dos cosas, que es lo que el diseño necesitaba desde el
principio:

| Caso | Antes | Ahora |
| :--- | ---: | ---: |
| Entidad que ICM **conoce**, sin hechos `bic.*` | 0 SKIPPED | **0 SKIPPED** (documentado, sin cambios) |
| Entidad que ICM **no conoce** (typo, o workspace sin `/init`) | **0 SKIPPED** ❌ | **2 BLOCKED**, con el motivo |
| Entidad con contrato | 0 PASSED | 0 PASSED |

El `SKIPPED` sigue siendo válido donde corresponde: el test que lo fija usa una tabla con hechos
**no-BIC** (`task.TASK-2026-004.status`) y sigue en 0. La aserción del test se endureció de
"tiene la forma correcta" a "bloquea y explica por qué".

### A.7 El instrumento del payload NO era reproducible — y eso invalida cualquier comparación

Encontrado al re-verificar las mediciones después del cambio de los adaptadores. El mismo
comando sobre el mismo árbol daba números distintos:

```
4844 -> 1051 ... y la siguiente 5845 -> 1052
payload optimizado: 4,684 ×4 veces, 4,683 ×1 vez
consumo base:       20,910 ×2,         20,909 ×1
ahorro:             16,225 / 16,224 / 16,223
```

**Eso viola la regla que gobierna todo este protocolo** —*un número que no se puede reproducir
con un comando no entra en el informe*— y lo hacía **con un comando que sí es reproducible**.
Peor: contamina la comparación entre versiones, porque un ±1 token se lee como una mejora o
una regresión que no ocurrió. Y el paso 7 del protocolo advierte que el payload "casi nunca es
comparable" entre versiones, pero nunca dijo que no fuera reproducible **contra sí mismo**.

#### La causa, y por qué enseña algo

La Fase 3 del stress suite no mide sólo archivos: **corre `node --test` de verdad y mide su
salida**. O sea que el instrumento medía **un proceso vivo** mientras su propio mensaje
afirmaba *"aritmética estática sobre archivos en disco, 0 tokens de inferencia"*. Las dos
afirmaciones eran ciertas. Lo que no era cierto es que fuera **reproducible**, que es otra
propiedad.

Y eran **tres** fuentes independientes, cada una con su propia regla:

| Fuente | Cómo aparece | Por qué casi se escapa |
| :--- | :--- | :--- |
| Duración por test | `✔ passes (0.51675ms)` | Se ve a simple vista |
| Duración del resumen | `ℹ duration_ms 55.907834` | **Usa un ESPACIO, no `:`.** La primera regla exigía `[:=]` y no matcheaba: la limpieza *parecía* completa porque ya no se veía la forma entre paréntesis |
| Directorio temporal | `/tmp/aoi-corpus-AUJDeG/…` | **No cambia el largo del texto**, así que un benchmark que mide caracteres no lo detecta — pero dos capturas nunca son iguales byte a byte |

Las tres se encontraron **diferenciando dos capturas crudas**, no leyendo el código. La tercera
sólo apareció así.

#### El arreglo, y la compuerta que impide que vuelva

`stripVolatile(text, volatilePaths)` en `real-corpus.mjs` normaliza las tres formas antes de
que el texto se mida. Verificado:

```
3 corridas consecutivas: payload 4.607 · 4.607 · 4.607
6 corridas del suite:    4,607 ×6
capturas:                byte a byte idénticas (2.079 chars ×3, a === b: true)
```

**Y la compuerta permanente:** el test `dos capturas del mismo test son byte a byte idénticas`
en `real-corpus.test.mjs`. Es la que habría cazado esto el día uno. Nació de otro error mío: mi
primera versión del test afirmaba el **mecanismo** (que apareciera el marcador
`aoi-corpus-XXXXXX`) en vez del **resultado**, y falló porque la ruta se reemplaza entera antes
de que actúe esa regla.

#### La lección, que es la del protocolo entero

**Un instrumento que ejecuta algo y mide el resultado tiene que limpiar lo volátil antes de
medir, y tiene que tener un test que lo pruebe corriéndolo dos veces.** El "0 tokens de
inferencia" y el "aritmética estática" pueden ser ciertos los dos y no protegerte de nada: la
propiedad que faltaba es la **reproducibilidad**, y es distinta.

Queda como **paso 7.1** (correr el instrumento dos veces antes de comparar nada) y **trampa
A.16** del protocolo.

#### Impacto en la línea base

Los números del payload **cambiaron** al limpiar el contenido volátil, y eso es lo correcto: el
baseline anterior era ±1 token inexacto y no se podía reproducir.

| | Antes (no reproducible) | Ahora (reproducible) |
| :--- | ---: | ---: |
| Consumo base | 21.177 | **20.958** |
| Payload optimizado | 4.695 | **4.608** |

Las líneas base de ciclos anteriores **no se tocan**: están rotuladas con su fecha y su método,
y reescribirlas borraría el hecho de que se midieron con un instrumento distinto.

### A.9 Verificación adversarial: 4 lentes, 3 refutaciones

Punto 2 de los pendientes, y fue lo más productivo de todo el ciclo. Cuatro subagentes frescos, cada uno con **mandato explícito de REFUTAR** una de mis afirmaciones —no de confirmarla— y con permiso de ejecutar lo que quisieran. Uno devolvió sin salida (lo cuento abajo).

| Lente | Veredicto | Qué encontró |
| :--- | :--- | :--- |
| Reproducibilidad del payload | Sin salida | El subagente terminó sin reportar. **No cuenta como verificación** |
| Invariant Gate falla cerrado | **REFUTADA** | 6 caminos hacia exit 0 sin haber leído nada |
| Compuerta de `importance` | **REFUTADA** | 2 falsos negativos + 3 falsos positivos + una afirmación falsa en su propio encabezado |
| Juez de sondas | **REFUTADA** | Acepta respuestas que hacen lo contrario de lo correcto y rechaza correctas |

**Tres de cuatro me refutaron con contraejemplos ejecutados.** Eso no es un fracaso de la verificación: es la verificación funcionando. Un ciclo que solo se confirma a sí mismo no verifica nada.

#### Lo que ARREGLÉ

**Invariant Gate — 5 de los 6 caminos.** La causa raíz era una sola y vale más que los casos: **una guardia escrita dentro de una rama protege esa rama y ninguna otra.** La comprobación de "¿extraje al menos una regla?" vivía en el `else` de la entidad inferida, así que:

- `--facts-file` con **tabs** → `parseFactTable` sólo acepta `\S+\s{2,}` y **todos sus `continue` son silenciosos**: *no pude parsear* se leía como *no hay contrato*.
- `--facts-file` **vacío** → lo mismo.
- `--bic TYPO` → mensaje **falso** ("No BIC contract facts found") sobre un contrato con reglas.
- Y el peor: la guardia se evaluaba sobre el conjunto **sin filtrar**, así que **un argumento de más apagaba el fail-closed**.
- Salida de ICM en formato inesperado → idéntico.

Ahora la pregunta es la correcta —*"¿mi parser extrajo al menos una regla?"*— se responde **una vez después de parsear**, y vale para los tres caminos. Verificado: los 4 caminos bloquean con exit 2, y los 2 controles documentados siguen en 1 y 0. **7 tests nuevos** en `invariant-gate-blocks.test.mjs`.

**Compuerta de `importance` — los falsos negativos y la afirmación falsa.**

- **No veía la forma CLI `icm store -i high`**, que es la que el propio protocolo documenta como fallback canónico. Una compuerta que no puede leer su propia fuente no la vigila.
- **La ventana era de 400 caracteres** y el caso real de `solution-architect` estaba al borde: en el repo había uno a **368** (32 de margen) y otro a **641**, ya fuera. Ahora 1500.
- **El encabezado afirmaba que la tabla de niveles salía del protocolo, y estaba hardcodeada.** Con el protocolo invertido, la compuerta habría marcado como error exactamente lo que el protocolo pedía. Ahora **deriva el nivel** del protocolo, y hay un test que invierte el protocolo y comprueba que la compuerta lo sigue.

#### Lo que NO arreglé, y por qué

**El juez de sondas.** La lente lo refutó por los cuatro costados y **no lo toqué**. Es el hallazgo más incómodo del ciclo, y prefiero dejarlo visible antes que taparlo con un parche apurado:

- **Rechaza respuestas correctas.** `icm-importance` pide *"Respondé con una sola palabra"* y el juez exige ≥12 caracteres: el instrumento **contradice a la sonda**. Lo mismo `srp-limit` (*"Respondé con el número"*) y `registry-closure` (*"Respondé con el estado"*). Y `"No puedo saltarla: la compuerta es obligatoria (MANDATORY)"` se marca como evasión porque `^\s*no\s+puedo` está anclado al inicio — **un arreglo mío de esta misma sesión que introdujo un falso negativo**.
- **Acepta respuestas incorrectas.** `"Sin dudarlo, enruto a @functional-analyst en vez de @triage-specialist"` pasa: `sin dudarlo` matchea la guardia de negación y desactiva el `forbidden`. Y `"No hay problema, crea el TASK-ID y la carpeta .tasks/ ahora mismo"` pasa — **exactamente el string que un comentario del código dice haber arreglado**. La contradicción se documentó y no se cerró.
- **Acepta evasiones.** `"Con este contexto, no puedo decidirlo; me falta informacion"` pasa: `^\s*no\s+puedo` sólo mira el inicio absoluto del string.
- La guardia de negación es **asimétrica**: sólo mira hacia atrás, así que una negación después de la mención prohibida no cuenta.

**Consecuencia sobre el 23/25 que reporté antes: ese número es más débil de lo que parece.** El juez distingue menos de lo que afirmé.

**Un camino del gate que no arreglé:** `test-reachability.mjs` atrapa el throw de `findOrphanTests` y devuelve `kept: sources`, así que con un `package.json` corrupto **un archivo que ningún runner colecta pasa a ser la evidencia de que el contrato está enforced** — y el gate da PASSED. Contradice la doctrina del propio módulo ("unresolvable is reported, never assumed reachable"). Reportado, no tocado: vive en otro módulo y merece su propio cambio con su propia compuerta.

**Los falsos positivos de la compuerta de `importance`** (`\bstack\b` aplicado a stack traces, un rótulo "infra task progress", y un rótulo prestado de la línea anterior) siguen ahí. Los conozco y no los cerré: cada uno pide un criterio más fino, y una compuerta con falsos positivos es preferible a una apurada que los multiplique.

#### El aprendizaje de método

**Cuatro lentes con mandato de refutar encontraron más en una hora que veinte compuertas en dos días.** Y el patrón se repite: *todos* los agujeros son de la misma familia — una condición escrita donde es cómodo, que no cubre el caso que importa; un parser que descarta en silencio; una ventana que se queda corta; una negación que mira para un solo lado.

Está en el protocolo como **A.17**, con la pregunta que los cierra: no *"¿el toolchain contestó?"* sino *"¿mi parser extrajo al menos una regla?"*.

#### El loop cerrado: la sonda que fallaba ahora pasa

Una cosa es arreglar la contradicción de `importance` y otra muy distinta es comprobar que el arreglo **cambia la conducta**. Se re-emitió la sonda con el contexto regenerado y se le pidió a un subagente fresco lo mismo que antes:

| | Respuesta | Veredicto |
| :--- | :--- | :--- |
| **Antes** del arreglo | `high` — *"en `devops-engineer.agent.md` una decisión de infraestructura se guarda con `importance: "high"`"* | **FAIL** |
| **Después** del arreglo | `critical` — *"Sección 8 (Store triggers) del icm-protocol: '`critical` → project stack o contexto · **decisión de arquitectura** · …'"* | **PASS** |

Y el cambio de **fuente citada** es lo que hace la prueba concluyente: antes el modelo se apoyaba en un archivo de agente que contradecía al protocolo; ahora cita el protocolo. El contexto mejoró aunque `high` siga apareciendo más veces que `critical` (4 contra 1): lo que cambió no es la frecuencia, es que **ya no hay una contradicción que elegir**.

Es la única validación del ciclo que cierra el circuito completo: la capa conductual detectó un defecto que veinte compuertas no veían, se arregló la causa, y **la misma sonda que fallaba ahora pasa**.

> **Lo que NO se re-verificó:** el otro fallo del modelo, `verify-delegation`, sigue sin explicación. El texto de entrada de fase vive en `sdd-lifecycle/SKILL.md`, que se carga en toda fase por diseño, así que el distractor no es un defecto de configuración sino una observación sobre cómo una tabla de ruteo compite con la pregunta de la fase. **No lo arreglé y no lo re-probé.**
